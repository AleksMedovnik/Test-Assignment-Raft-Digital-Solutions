# ТЗ на загрузку данных из SRM API

**Статус документа:** проектирование. Реализация не входит ни в первый релиз (недели 1–4), ни в этап 2 (недели 5–8). По scope из [01_discovery.md](../01_discovery.md) интеграция с SRM отнесена за горизонт восьми недель. Документ снимает неопределённость до начала работ.

**Обозначения по всему документу.** *Факт* — прямо следует из фрагмента API в TS.docx, раздел 1.3, или из артефактов Блоков 2–3. *Решение* — архитектурный выбор. *Допущение* — то, чего в контракте нет и что принято рабочей гипотезой. *Открытый вопрос* — то, что обязан подтвердить владелец API до старта реализации.

## 0. Что известно об API (факты)

Всё, что ниже, взято из фрагмента в TS.docx 1.3 дословно. Ничего сверх этого не предполагается.

| Endpoint | Параметры | Что известно |
|---|---|---|
| `GET /api/v2/contracts` | `page`, `size` (max 100), `updatedFrom` (ISO8601) | Список договоров. В ответе есть заголовок `X-Total-Count` |
| `GET /api/v2/tenders` | `page`, `size` (max 100) | **Параметра `updatedFrom` нет.** Всего ~180 тыс. записей. Сортировка по релевантности, **порядок между вызовами не гарантируется** |
| `GET /api/v2/tenders/{id}/lots` | — | Лоты одного тендера. **Только поштучно, батч-метода нет** |

**Авторизация:** OAuth2 `client_credentials`, **TTL токена 15 минут**.
**Лимит: 100 req/min на токен.**

### Открытые вопросы к владельцу API

Ни один из них не обойдён догадкой — там, где ответ влияет на архитектуру, ниже описано поведение при худшем варианте.

1. Возвращает ли `/tenders` заголовок `X-Total-Count`? В контракте он указан только для `/contracts`. От этого зависит, чем закрывается контроль полноты выгрузки.
2. Существует ли `GET /api/v2/tenders/{id}` (карточка одного тендера)? В контракте есть только `/lots`. Влияет на то, как проверять существование записи.
3. Есть ли у `/tenders` параметр сортировки (`sort`, `orderBy`)? Стабильная сортировка по `id` радикально упростила бы постраничный обход.
4. Возвращает ли API при 429 заголовок `Retry-After`?
5. Лимит 100 req/min объявлен «на токен». Допускается ли клиенту держать несколько токенов одновременно, или это будет расценено как обход лимита? **До получения ответа проектируем строго на один токен.**
6. Каков объём `/contracts`? В материалах он не назван.
7. Что происходит с тендером после отмены или архивации — исчезает из выдачи `/tenders` или остаётся со статусом?
8. Состав полей `/tenders` и `/lots` в материалах не приведён. Схема будет зафиксирована по факту первого обследования (см. раздел 8).

## 1. Цель интеграции

### Какие сущности загружаются

| Сущность | Endpoint | Зачем нужна |
|---|---|---|
| Договоры | `/contracts` | Контрактные цены и условия поставки |
| Тендеры | `/tenders` | История конкурентных процедур, связь закупки с процедурой |
| Лоты тендеров | `/tenders/{id}/lots` | Позиционный состав процедуры: номенклатура, количество, цены предложений |

### Для каких аналитических задач

Эти данные закрывают то, чего в закупочной витрине первого релиза структурно нет. Из [02_model.md](../02_model.md) и из результатов Блока 3:

1. **Контрактная цена как эталон сравнения.** Ключевой вывод Блока 3: в данных 1С отсутствует эталонная цена позиции — коэффициент вариации цены внутри группы «позиция + единица» равен 0,543 при глобальном 0,576, `plan_price` ведёт себя так же (CV 0,551, все значения уникальны). Сравнивать фактическую цену можно только с ценами других поставщиков, а не с обязательством. Контрактная цена из SRM даёт недостающую точку отсчёта и превращает метрику 3 из матрицы Блока 2 («потенциал экономии») из статистической в договорную.
2. **Отклонение факта закупки от условий договора** — прямой ответ на вопрос Смирнова «где мы переплачиваем», не зависящий от разброса рыночных цен.
3. **Аналитика тендеров** — доля закупок, прошедших конкурентную процедуру, и разница между ценой победителя и фактической ценой закупки.

### В какие слои попадают данные

Слои — те же, что в [02_model.md](../02_model.md), новых не вводится:

```
SRM API → ingestion (raw.srm_*) → stg.srm_* → ods.srm_* → dds (измерение + меры) → mart
```

### Какие целевые сущности модели обогащаются

Блок 2 в разделе самопроверки зафиксировал: «Добавление контрактных цен из SRM — новое измерение и мера в существующем факте, без изменения зерна». Это решение сохраняется без изменений:

| Объект модели | Изменение | Влияние на зерно |
|---|---|---|
| `dds.dim_contract` | новое измерение: договор, поставщик, период действия, валюта | нет |
| `dds.fact_po_line` | новые поля `contract_key` (FK, nullable) и `contract_price` | **зерно не меняется** — одна действующая строка заказа |
| `dds.dim_tender`, `dds.fact_tender_lot` | тендеры и лоты; зерно `fact_tender_lot` — один лот одного тендера | отдельная фактовая таблица, к `fact_po_line` не присоединяется напрямую |

**Открытый вопрос:** содержит ли SRM ссылку на заказ поставщику в 1С. Без неё связь «договор → строка заказа» строится по паре «поставщик + номенклатура + период действия договора», что даёт неоднозначность при перекрывающихся договорах. Это ключевой вопрос ценности всей интеграции, и его следует задать до начала работ.

## 2. Схема загрузки и ответственность этапов

| Этап | Ответственность | Что делает | Чего НЕ делает |
|---|---|---|---|
| **Ingestion** | получить данные и не потерять | HTTP-вызовы, соблюдение лимита, retry, токен, ведение очереди и checkpoint | не интерпретирует содержимое |
| **raw** | неизменяемый след ответа API | JSONB-payload как есть + метаданные: `scan_id`, `fetched_at`, `endpoint`, `page`, `http_status`, `payload_hash` | не типизирует, не чистит, не дедуплицирует |
| **stg** | типизация и стандартизация | разбор JSON в колонки, приведение типов, нормализация дат к UTC, тримминг строк | не применяет бизнес-правила |
| **validation (dq)** | пропустить дальше только пригодное | schema validation, обязательность полей, ссылочная целостность, контроль полноты выгрузки, quarantine | не исправляет данные молча |
| **ods** | историчность и разрешение версий | SCD2 для договоров, определение действующей версии, дедупликация по бизнес-ключу | не считает метрики |
| **dds / mart** | аналитическая модель Блока 2 | заполнение `dim_contract`, `fact_tender_lot`, обогащение `fact_po_line` | — |

**Решение: raw хранится вечно и никогда не перезаписывается.** Причина конкретная — состав полей `/tenders` и `/lots` в материалах не приведён (открытый вопрос 8). Если после первой выгрузки окажется, что нужное поле мы не разобрали, повторная выгрузка 180 тыс. записей стоит 30 часов работы API. Сырой payload позволяет перепарсить без единого обращения к источнику.

## 3. Инкрементальная загрузка `/tenders` без `updatedFrom`

Это центральная задача интеграции, поэтому разбирается подробно.

### 3.1. Почему offset-based инкремент здесь небезопасен

**Факт:** сортировка `/tenders` — по релевантности, порядок между вызовами не гарантирован.

Постраничный обход 1 800 страниц при нестабильной сортировке даёт два эффекта одновременно: часть записей попадает в выдачу дважды (на разных страницах), часть не попадает ни на одну. Запомнить «дошли до страницы N» бессмысленно — на следующем запуске страница N будет содержать другие записи. Поэтому запоминание позиции (offset/page) как единственного механизма инкремента исключено.

### 3.2. Ключевое наблюдение, на котором строится решение

Считаем стоимость обхода в запросах:

| Операция | Запросов | Время при 100 req/min |
|---|---:|---:|
| Полный обход списка `/tenders` (1 800 страниц по 100) | **1 800** | **18 минут** |
| Загрузка лотов для всех 180 тыс. тендеров (поштучно) | **180 000** | **30 часов** |

**Полный обход списка стоит 18 минут — его можно делать ежедневно.** Дорогая часть — лоты, потому что метод поштучный. Отсюда решение:

> **Решение.** Инкремент строится не на списке, а на лотах. Список тендеров пересканируется ПОЛНОСТЬЮ каждую ночь и сравнивается с предыдущим снимком по хешу содержимого. Лоты дозагружаются только для новых и изменившихся тендеров.

Это снимает проблему отсутствия `updatedFrom` целиком: нам не нужен фильтр по дате, потому что мы читаем всё. И снимает проблему порядка: мы не полагаемся на позицию, а собираем множество.

### 3.3. Что хранится как state

Две таблицы. Ни в одной нет «указателя на позицию» — только состояние по каждой сущности.

```sql
-- Снимок состояния тендера: что мы видели в последний раз
CREATE TABLE ods.srm_tender_state (
    tender_id          text PRIMARY KEY,
    payload_hash       text        NOT NULL,   -- хеш нормализованного payload из списка
    first_seen_scan_id bigint      NOT NULL,
    last_seen_scan_id  bigint      NOT NULL,   -- в каком скане видели последний раз
    last_changed_at    timestamptz NOT NULL,   -- когда payload_hash менялся
    lots_fetched_hash  text,                   -- для какого payload_hash уже загружены лоты
    lots_fetched_at    timestamptz,
    missing_scan_count smallint    NOT NULL DEFAULT 0,  -- подряд сканов без этой записи
    status             text        NOT NULL DEFAULT 'active'
                       CHECK (status IN ('active','suspected_missing','gone'))
);

-- Журнал сканов: полнота и сходимость
CREATE TABLE ods.srm_scan_run (
    scan_id           bigserial PRIMARY KEY,
    started_at        timestamptz NOT NULL,
    finished_at       timestamptz,
    pages_requested   int,
    ids_seen_distinct int,
    total_count_header int,        -- если /tenders отдаёт X-Total-Count (открытый вопрос 1)
    coverage_pct      numeric(5,2),
    status            text NOT NULL CHECK (status IN ('running','ok','incomplete','failed'))
);
```

`payload_hash` — SHA-256 от канонизированного JSON записи (отсортированные ключи, исключены волатильные поля вроде `relevanceScore`, если такие обнаружатся при обследовании). Хеш и есть замена отсутствующему `updatedAt`.

### 3.4. Алгоритм ночного скана

```
1. scan_id = новый прогон
2. для page = 1..N, пока страница непустая:
       GET /api/v2/tenders?page={page}&size=100
       записать сырой ответ в raw.srm_tenders (scan_id, page)
3. по всем полученным записям (множество, дубли схлопываются по tender_id):
       новый tender_id            -> INSERT state, пометить лоты к загрузке
       payload_hash изменился     -> UPDATE state, last_changed_at = now, пометить лоты к загрузке
       payload_hash тот же        -> UPDATE last_seen_scan_id
4. записи в state со status='active', не встреченные в этом скане:
       missing_scan_count += 1
5. поставить в очередь загрузку лотов для помеченных тендеров
6. закрыть scan_run: ids_seen_distinct, coverage_pct
```

### 3.5. Как предотвращается потеря изменённых записей

Три независимых механизма, работающих вместе:

1. **Полное чтение каждую ночь.** Изменение не может «уехать» за границу окна, потому что окна нет — читается весь набор.
2. **Мультипроходная сходимость.** Пропуск записи при нестабильной сортировке — событие случайное и независимое между прогонами. Если один проход пропускает долю *p* записей, два прохода пропускают *p²*, три — *p³*. **Решение:** ночной скан выполняется в **два прохода** (2 × 1 800 = 3 600 запросов, 36 минут) с объединением множеств идентификаторов. Третий проход добавляется, если `coverage_pct` устойчиво ниже порога.
3. **Контроль полноты.** Если `/tenders` отдаёт `X-Total-Count` (открытый вопрос 1), покрытие считается как `ids_seen_distinct / X-Total-Count`. Порог: **≥ 99,5%** — скан со статусом `ok`. Ниже — статус `incomplete`, добавляется ещё один проход, срабатывает алерт. Если заголовка нет, покрытие оценивается косвенно: доля идентификаторов из предыдущего снимка, встреченных в текущем скане. Резкое падение этой доли означает либо проблему с выдачей API, либо массовое изменение на стороне SRM — в обоих случаях нужен человек.

### 3.6. Как обнаруживаются новые и изменённые записи

- **Новые:** `tender_id` отсутствует в `ods.srm_tender_state`.
- **Изменённые:** `payload_hash` отличается от сохранённого. Это работает без `updatedAt` и без доверия к порядку, но имеет известное ограничение: **изменения, не отражённые в полях списка, невидимы.** Если лоты тендера поменялись, а карточка в списке — нет, хеш не изменится. Это закрывается периодическим reconciliation (раздел 3.8).

### 3.7. Исчезнувшие и отменённые записи

**Решение: запись никогда не удаляется по факту одного отсутствия в выдаче** — при негарантированном порядке отсутствие может быть обычным пропуском пагинации.

```
missing_scan_count = 1..2   -> status остаётся 'active', ничего не происходит
missing_scan_count = 3      -> status = 'suspected_missing', проверка существования
missing_scan_count >= 5     -> status = 'gone', в аналитике помечается как недоступный
```

**Проверка существования:** `GET /api/v2/tenders/{id}/lots`. Это единственный документированный endpoint с обращением по идентификатору. Ответ 404 — запись действительно удалена; ответ 200 — запись жива, а её отсутствие в списке было пропуском пагинации, счётчик сбрасывается. Стоимость проверки — 1 запрос на подозрительную запись.

**Решение: в аналитической модели удаление мягкое.** Тендер со `status='gone'` остаётся в `dim_tender` с признаком, исторические факты не переписываются — иначе отчёт за прошлый период изменится задним числом, что прямо противоречит требованию drill-down и воспроизводимости из Блока 2.

### 3.8. Периодический reconciliation scan

**Зачем нужен, помимо ночного:** ночной скан не видит изменений, не отражённых в карточке списка (см. 3.6), — прежде всего изменений состава лотов.

| Параметр | Значение | Обоснование |
|---|---|---|
| Частота | **раз в неделю**, в выходные | Компромисс между свежестью и нагрузкой |
| Объём | полная перезагрузка лотов для **среза** тендеров, а не для всех | Полная перезагрузка всех лотов = 30 часов, еженедельно неприемлемо |
| Срез | все тендеры со статусом «активная процедура» + случайная выборка 5% остальных | Активные меняются, завершённые практически нет |
| Стоимость | при 10 тыс. активных + 8,5 тыс. выборки ≈ **18 500 запросов ≈ 3 часа** | Укладывается в выходное окно |
| Полный reconciliation всех лотов | **раз в квартал**, как отдельная плановая работа на 30+ часов | Гарантия того, что дрейф не накапливается годами |

**Влияние на API:** ночной скан занимает 36 минут в двух проходах плюс лоты изменённых; недельный reconciliation — 3 часа в выходные; квартальный — 30+ часов, согласовывается с владельцем API заранее. Ни одна из операций не выходит за 100 req/min.

### 3.9. Идемпотентность

- **raw:** уникальность `(scan_id, endpoint, page)`; повторная запись той же страницы того же скана перезаписывает строку, а не добавляет.
- **stg/ods:** upsert по бизнес-ключу — `tender_id` для тендеров, `(tender_id, lot_id)` для лотов. `INSERT ... ON CONFLICT DO UPDATE`.
- **Следствие:** повторный запуск любого этапа на тех же данных даёт тот же результат. Это условие того, что resume после сбоя (раздел 6) безопасен.

## 4. Rate limit: 100 req/min при 180 тыс. записей

### 4.1. Арифметика первичной загрузки

**Факты:** лимит 100 req/min на токен; `/tenders` ~180 тыс. записей; `size` max 100; лоты только поштучно.

| Фаза | Формула | Запросов | Время |
|---|---|---:|---:|
| Обход списка тендеров | 180 000 / 100 | 1 800 | 18 мин |
| Лоты, по одному на тендер | 180 000 × 1 | 180 000 | 30,0 ч |
| **Итого** | | **181 800** | **30,3 ч** |
| С запасом 10% на retry, refresh токена, повторы | | ~200 000 | **~33 ч** |

**Первичная загрузка занимает порядка полутора суток непрерывной работы.** Это не оптимизируется: 180 тыс. поштучных вызовов при 100 req/min — жёсткая нижняя граница, заданная контрактом API.

### 4.2. Что из этого следует для архитектуры

1. **Первичная загрузка — не задача ночного пайплайна, а отдельный длительный backfill-процесс** с собственной очередью и checkpoint, работающий несколько суток и переживающий рестарты.
2. **Запуск интеграции нельзя планировать «в ночь перед демонстрацией».** В план работ закладывается ≥ 3 суток на первичную загрузку с учётом сбоев.
3. **Данные становятся доступны инкрементально, а не разом.** Договоры (`/contracts`, есть `updatedFrom`) загружаются первыми и быстро; тендеры без лотов — за 18 минут; лоты приезжают порциями в течение полутора суток. Витрины проектируются так, чтобы работать на неполном наборе лотов и честно показывать покрытие.
4. **Ежедневный инкремент дёшев** и в ночное окно укладывается свободно:

| Операция | Запросов | Время |
|---|---:|---:|
| Скан списка, 2 прохода | 3 600 | 36 мин |
| Лоты изменённых тендеров (допущение: 1% в сутки) | 1 800 | 18 мин |
| Договоры инкрементально | зависит от объёма | минуты |
| **Итого ночью** | **~5 400** | **~55 мин** |

**Допущение:** суточная доля изменившихся тендеров принята за 1%. В материалах этой величины нет; она измеряется на первой же неделе работы по `srm_tender_state.last_changed_at` и уточняется. При 5% изменений ночное окно вырастает до ~2,5 часов — всё ещё приемлемо.

### 4.3. Очередь запросов и ограничитель скорости

**Решение: персистентная очередь работ в PostgreSQL, а не в памяти процесса.** Очередь в памяти теряется при рестарте, а рестарт за 33 часа гарантирован.

```sql
CREATE TABLE ods.srm_fetch_queue (
    queue_id     bigserial PRIMARY KEY,
    endpoint     text        NOT NULL,     -- 'tenders_page' | 'tender_lots' | 'contracts_page'
    resource_key text        NOT NULL,     -- номер страницы или tender_id
    scan_id      bigint,
    priority     smallint    NOT NULL DEFAULT 100,
    status       text        NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','in_progress','done','failed','quarantined')),
    attempts     smallint    NOT NULL DEFAULT 0,
    last_error   text,
    locked_by    text,
    locked_at    timestamptz,
    completed_at timestamptz,
    CONSTRAINT uq_srm_queue UNIQUE (endpoint, resource_key, scan_id)
);
CREATE INDEX ix_srm_queue_pending ON ods.srm_fetch_queue (priority, queue_id)
    WHERE status = 'pending';
```

Забор задачи — `SELECT ... FOR UPDATE SKIP LOCKED LIMIT n`: несколько воркеров не возьмут одну задачу.

**Ограничитель скорости.** Лимит объявлен на токен, а токен общий, поэтому **ограничитель обязан быть общим для всех воркеров**, а не локальным. Реализация — token bucket в Redis либо, чтобы не вводить лишнюю технологию, счётчик в той же PostgreSQL с окном в одну минуту и атомарным инкрементом. Параметры: ёмкость 100, пополнение 100/мин, **рабочая уставка 90 req/min** — 10% запаса под проверки существования и refresh токена, чтобы плановая работа не выедала лимит целиком.

### 4.4. Допустимая параллельность

Здесь важно не ошибиться в сторону «больше воркеров — быстрее».

Пропускная способность жёстко ограничена 100 req/min = **1,67 req/s**. При типичной задержке ответа 200–500 мс один воркер обеспечивает 2–5 req/s, то есть **один воркер уже перекрывает лимит**. Увеличение параллельности не ускоряет загрузку ни на минуту — оно лишь увеличивает конкуренцию за общий bucket.

**Решение: 2–4 воркера, не больше.** Смысл второго и последующих — не пропускная способность, а устойчивость: пока один ждёт ответа или медленный retry, другой продолжает выбирать лимит. Верхняя граница 4 выбрана из того, что при 1,67 req/s и 500 мс задержки этого достаточно с запасом.

### 4.5. Retry policy и backoff

| Ситуация | Retryable | Политика |
|---|---|---|
| 429 | да | Пауза до конца текущего минутного окна; если есть `Retry-After` (открытый вопрос 4) — по нему. Экспонента 60 → 120 → 300 с, jitter ±20%. Не считается неудачной попыткой первые 3 раза |
| 5xx | да | Экспонента 1 → 2 → 4 → 8 → 16 → 32 с, jitter, максимум 5 попыток |
| Timeout, сетевой сбой | да | Та же экспонента. Безопасно, так как все вызовы — GET |
| 401 | да, один раз | Refresh токена, ровно одна повторная попытка (см. раздел 5) |
| 403 | **нет** | Прав нет, повтор не поможет. `status='failed'`, алерт |
| 404 на `/lots` | не ошибка | Значимый ответ: тендер отсутствует. Обрабатывается логикой 3.7 |
| Некорректный payload | **нет** | `status='quarantined'`, сырой ответ сохраняется, алерт |
| Частичная недоступность endpoint | да | Circuit breaker per endpoint: 10 подряд 5xx → пауза 15 мин, остальные endpoint работают |

После исчерпания попыток задача переходит в `failed` и остаётся в очереди — она не теряется и может быть переоткрыта вручную или следующим прогоном.

### 4.6. Сохранение прогресса и продолжение после остановки

Прогресс — это состояние строк `srm_fetch_queue` и `srm_tender_state`, а не позиция в цикле. Никакого состояния в памяти процесса не хранится. Задачи, «зависшие» в `in_progress` дольше 15 минут (упал воркер), возвращаются в `pending` сторожевым процессом по `locked_at`.

## 5. Аутентификация и протухший токен

**Факт:** OAuth2 `client_credentials`, TTL токена 15 минут. При 100 req/min один токен покрывает не более 1 500 запросов; при первичной загрузке в ~182 тыс. запросов потребуется **порядка 150 обновлений токена**. Это штатная частая операция, а не редкое событие.

### Хранение

Секреты (`client_id`, `client_secret`) — в секрет-хранилище контура (Vault, secrets менеджера оркестратора или защищённые переменные окружения). **В конфигурации репозитория, в коде и в логах их нет.** Действующий access token хранится в одной строке служебной таблицы, доступной всем воркерам:

```sql
CREATE TABLE ods.srm_token (
    token_id     smallint PRIMARY KEY DEFAULT 1 CHECK (token_id = 1),
    access_token text        NOT NULL,   -- шифруется на уровне СУБД/диска
    obtained_at  timestamptz NOT NULL,
    expires_at   timestamptz NOT NULL,
    refreshed_by text
);
```

### Определение истечения и proactive refresh

**Решение: обновление проактивное, по времени, плюс реактивное по 401 как страховка.**

- Проактивно: воркер обновляет токен, если до `expires_at` осталось меньше **20% TTL, то есть 3 минуты**. Порог выбран так, чтобы длинный retry с backoff до 300 секунд не начался с токеном, который истечёт в процессе.
- Реактивно: 401 всё равно возможен — часы клиента и сервера расходятся, сервер может отозвать токен. Обработка описана ниже.

Полагаться только на 401 нельзя: при 4 воркерах каждое истечение даёт пачку одновременных 401 и всплеск лишних запросов, а они выедают лимит 100 req/min.

### Как избежать одновременного refresh

**Решение: advisory lock в PostgreSQL.** Технология уже есть в контуре, вводить координатор не требуется.

```
если токен скоро истекает:
    pg_try_advisory_lock(SRM_TOKEN_LOCK)
      получен  -> перечитать строку (возможно, обновил другой), при необходимости
                  запросить новый токен, записать, снять лок
      не получен -> подождать 200 мс, перечитать строку из БД и продолжить с новым токеном
```

Перечитывание строки после получения лока обязательно: иначе два воркера, дошедшие до порога одновременно, сделают два обращения к OAuth-серверу подряд.

### Что происходит с запросом, получившим 401

1. Запрос **не считается провалившимся** — он возвращается в очередь в статусе `pending`, счётчик попыток увеличивается.
2. Воркер инициирует refresh по процедуре выше.
3. Запрос повторяется **ровно один раз** с новым токеном. Повторный 401 после свежего токена означает проблему с правами или учётной записью — это `failed` и алерт, а не бесконечный цикл.

**Безопасность повторного выполнения** обеспечена природой операций: все вызовы — `GET`, побочных эффектов нет, повтор идемпотентен по определению. Запись в raw идёт с ключом `(scan_id, endpoint, page)`, поэтому повторно полученная страница перезаписывает саму себя, а не создаёт дубль.

## 6. Сбой на 130-й тысяче: механизм восстановления

Сценарий: идёт первичная загрузка лотов, обработано 130 000 тендеров из 180 000, процесс упал.

### Что уже считается успешно обработанным

Задача считается выполненной только после того, как сырой ответ **записан в raw и зафиксирован в транзакции** вместе с переводом строки очереди в `done`:

```sql
BEGIN;
  INSERT INTO raw.srm_tender_lots (tender_id, scan_id, payload, fetched_at, http_status)
  VALUES (...)
  ON CONFLICT (tender_id, scan_id) DO UPDATE SET payload = EXCLUDED.payload, ...;

  UPDATE ods.srm_fetch_queue
     SET status = 'done', completed_at = now()
   WHERE endpoint = 'tender_lots' AND resource_key = $1 AND scan_id = $2;

  UPDATE ods.srm_tender_state
     SET lots_fetched_hash = $3, lots_fetched_at = now()
   WHERE tender_id = $1;
COMMIT;
```

Из этого следует главное: **промежуточных состояний не существует.** Тендер либо полностью загружен и отмечен, либо не загружен вовсе. Ситуация «данные записались, а отметка не проставилась» невозможна, потому что это одна транзакция.

### Где хранится checkpoint

Checkpoint — не число и не позиция в цикле, а **состояние 180 тысяч строк очереди**. После падения в таблице: 130 000 строк `done`, часть `in_progress` (те, что воркеры держали в момент падения), остальные `pending`.

### Что происходит при рестарте

```
1. Сторожевой процесс: строки in_progress с locked_at старше 15 минут -> pending.
   Это безопасно: транзакция незавершённых задач откатилась, данных в raw по ним нет.
2. Воркеры стартуют и выбирают pending через FOR UPDATE SKIP LOCKED.
3. Загрузка продолжается ровно с 130 001-й записи.
```

**Повторно сканировать уже загруженное не требуется.** Это принципиально: перезагрузка 130 000 лотов стоила бы 21,7 часа впустую. Остаток в 50 000 запросов занимает **500 минут ≈ 8,3 часа**.

### Как предотвращаются дубли

Тремя уровнями сразу: уникальный ключ очереди `(endpoint, resource_key, scan_id)`; `ON CONFLICT DO UPDATE` при записи в raw по `(tender_id, scan_id)`; upsert по `(tender_id, lot_id)` при разборе в stg/ods. Даже если задача выполнится дважды, результат будет тем же.

### Когда нужно частичное пересканирование

Один случай: если между падением и рестартом прошло столько времени, что снимок списка устарел. **Решение:** если `scan_run.started_at` старше **24 часов**, перед продолжением загрузки лотов заново прогоняется скан списка (18–36 минут) и очередь дополняется появившимися и изменившимися тендерами. Уже загруженные лоты при этом не трогаются — сравнение идёт по `lots_fetched_hash`.

## 7. Классификация ошибок

**Retryable** — 429, 5xx, timeout, разрыв соединения, 401 (однократно после refresh).
**Non-retryable** — 403, 400 при корректно сформированном запросе, некорректный или неразбираемый payload, нарушение схемы.

Non-retryable не удаляются из очереди: они получают статус `failed` или `quarantined` и остаются видимыми. Молчаливое исчезновение задачи — худший из возможных исходов, потому что оно неотличимо от успеха.

## 8. Контроль качества

| Проверка | Как выполняется | Реакция |
|---|---|---|
| **Полнота выгрузки** | `ids_seen_distinct` против `X-Total-Count` (для `/contracts` — факт, для `/tenders` — открытый вопрос 1) | < 99,5% → статус скана `incomplete`, дополнительный проход, алерт |
| **Контроль пропусков** | Доля идентификаторов из предыдущего снимка, встреченных в текущем скане | Падение более чем на 2 п.п. — алерт |
| **Покрытие лотами** | Доля тендеров, у которых `lots_fetched_hash = payload_hash` | Выводится на витрину как показатель зрелости данных |
| **Schema validation** | JSON Schema на stg, до типизации | Нарушение → quarantine, загрузка не падает |
| **Quarantine** | `raw.srm_quarantine`: payload, ошибка, время, scan_id | Разбор вручную; после исправления парсера — переигрывается из raw без обращения к API |
| **Ссылочная целостность** | Лот ссылается на существующий тендер; договор — на существующего поставщика (по ИНН, через золотую запись Блока 2) | Неизвестный поставщик → Unknown-член измерения, как в Блоке 2, факт не теряется |
| **Метрики ingestion** | запросов за прогон, доля 429/5xx, среднее время ответа, длительность прогона, глубина очереди, число `failed` и `quarantined` | Пишутся в `dq.run_metric` — таблицу из DDL Блока 2, новых сущностей не вводится |

## 9. Observability

**Логи.** Структурированные, по одной записи на попытку запроса: `scan_id`, endpoint, `resource_key`, попытка, HTTP-код, длительность, размер ответа, `worker_id`. **Токен и секреты не логируются ни в каком виде, включая заголовки.**

**Метрики.** Скорость (req/min) против уставки 90; распределение HTTP-кодов; глубина очереди `pending`; число `failed` и `quarantined`; возраст самой старой `pending`-задачи; число refresh токена за час (аномальный рост — признак проблемы с часами или отзывом токенов); `coverage_pct` последнего скана.

**Алерты.**

| Условие | Кому | Срочность |
|---|---|---|
| Скан завершился со статусом `incomplete` | дата-инженер | в течение дня |
| Более 10 задач в `failed` за прогон | дата-инженер | немедленно |
| 403 на любом endpoint | дата-инженер + владелец API | немедленно |
| Токен не обновляется (нет успешного refresh 20 минут) | дата-инженер | немедленно |
| Последняя успешная загрузка старше 48 часов | дата-инженер + РП | немедленно |
| Доля 429 выше 5% запросов | дата-инженер | в течение дня |

**Статус последней успешной загрузки** публикуется в общий механизм свежести данных, описанный в [04_pipeline.md](04_pipeline.md): отдельная строка на источник SRM с `data_as_of`, `last_success_at` и покрытием лотами. Заказчик видит его на дашборде наравне со свежестью 1С — иначе неполнота данных SRM останется невидимой ровно до момента, когда по ней примут решение.
