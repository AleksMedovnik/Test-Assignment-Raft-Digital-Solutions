## Порядок выполнения

Из корня проекта, по порядку:

```bash
set -a; . ./.env; set +a
psql -v ON_ERROR_STOP=1 -f 03_sql/00_load_raw.sql    # схема raw + \copy семи CSV
psql -v ON_ERROR_STOP=1 -f 02_ddl.sql                # целевые таблицы Блока 2, без изменений
psql -v ON_ERROR_STOP=1 -f 03_sql/01_transform.sql   # ETL raw -> ods/dds/mart/dq
psql --csv -f 03_sql/q1_otif.sql                  -o 03_sql/q1_result.csv
psql --csv -f 03_sql/q2_price_anomalies.sql       -o 03_sql/q2_result.csv
psql --csv -f 03_sql/q3_supplier_concentration.sql -o 03_sql/q3_result.csv
```

`00_load_raw.sql` использует `\copy` (клиентская загрузка), поэтому серверу не нужен доступ к файлам, а скрипт запускается из корня проекта — пути к `data/*.csv` относительные.

## Допущения

1. **Слияние дублей поставщиков подтверждено в скрипте.** Модель Блока 2 требует ручного подтверждения владельцем справочника и по умолчанию не сливает записи. В `01_transform.sql`, шаг 4.3, подтверждение имитировано (`confirmed_by = 'demo: подтверждение по совпадению ИНН'`), иначе 8 пар учётных записей с одним ИНН попали бы в отчёты как разные юрлица и рейтинг поставщиков был бы заведомо неверен. В продуктиве это задача стюарда, а не шаг ETL.
2. **Эталонная категория — колонка `category`.** Расхождение с `category_reported` (33 позиции) помечено флагом `has_category_conflict`. Выбор эталона по Блоку 2 — решение категорийного менеджмента.
3. **Единица измерения приёмки.** В `receipts.csv` колонки единицы нет, поэтому `qty_received` считается выраженным в той же единице, что и строка заказа. Проверка Блока 2 это подтверждает косвенно: превышений над максимальным заказанным количеством по всем версиям строки нет ни одного.
4. **Курс — на дату размещения заказа**, выходные закрыты протяжкой последнего известного курса. Правило зафиксировано в Блоке 2 как допущение, подлежащее утверждению заказчиком.
5. **`is_price_scale_suspect` вычисляется правилом, а не хардкодом валюты**: медиана цены за базовую единицу по валюте сравнивается с рублёвой базой на одинаковых парах «позиция + базовая единица», отклонение более чем втрое помечает валюту. На данных правило самостоятельно нашло CNY (2 533 строки, 4,76%).

## Расхождения между моделью Блока 2 и данными, зафиксированные явно

Оба расхождения описаны в шапках соответствующих SQL-файлов. Определения метрик при этом не менялись — менялся периметр, на котором метрика расчётна.

### 1. Поток приёмок обрывается раньше конца календарного месяца (Q1)

Приёмки в датасете заканчиваются 2026-08-12, плановые даты доходят до 2026-09-26. Доля строк без единой приёмки по месяцам: 5,6–8,2% в январе–июле 2026 и **58,5% в августе** — то есть август календарно полон, а фактом покрыт наполовину. Поэтому граница окна в Q1 берётся как минимум из двух: начало текущего календарного месяца и начало месяца водяного знака полноты факта. Итоговое окно — **2026-02-01 … 2026-07-31**.

### 2. Цена не масштабируется вместе с единицей измерения (Q2)

Медианная цена строки составляет около 20 000 руб при любом коэффициенте единицы: KG (×1) — 20 281, TON (×1000) — 20 158, PACK24 (×24) — 19 702, ROLL50 (×50) — 19 904. Деление на `factor_to_base` разносит цену внутри одной базовой единицы в 1000 раз и порождает отклонения в миллионы процентов, отражающие упаковку, а не переплату.

Поэтому в Q2 группа сравнения сужена с «позиция + базовая единица» до **«позиция + код единицы»** — сравниваются закупки в одинаковой упаковке. Отображаемая цена остаётся ценой за базовую единицу: внутри группы это деление на константу, на сравнение не влияющее. В квартале остаётся 1 036 групп с двумя и более поставщиками.

**Следствие для Блока 2, требующее правки при следующей ревизии модели:** витрина `mart.price_benchmark` сгруппирована по `base_uom_code` и на таких данных подвержена тому же артефакту. Документы Блока 2 в этой задаче не изменялись, поэтому здесь это только зафиксировано.

## Что требует ручной проверки и решения заказчика

1. **Параметры методики OTIF.** Допуск по сроку (0 дней), допуск по количеству (0%), учёт только `accepted` в In Full, исключение отменённых строк, версия плана на плановую дату — это версия v1 из Блока 2, вынесенная в CTE `params` запроса Q1. Утверждает владелец метрики; после утверждения параметры переносятся в конфигурационную таблицу.
2. **Порог «≥20 поставок» на этих данных ничего не отсекает.** Минимальное число строк заказа у поставщика за окно — 43, порог проходят все 120 поставщиков. Фильтр реализован и работает, но его действие на реальном датасете проверить нельзя.
3. **Смысл результата Q2.** Запрос корректен, но в датасете цена сгенерирована независимо от позиции: коэффициент вариации цены внутри группы «позиция + единица» равен 0,543 при глобальном 0,576, средний размах max/min внутри группы — 25,6 раза, `plan_price` ведёт себя так же (CV 0,551, все значения уникальны). Эталонной цены позиции в данных нет, поэтому полученный Топ-15 — хвост случайного распределения, а не свидетельство переплаты. На реальных данных 1С:УТ тот же запрос даёт содержательный результат.
4. **Порядок сортировки Q2.** Топ-15 отбирается по модулю отклонения от медианы — прямое прочтение постановки. Если бизнесу нужен список для действия, сортировать следует по `deviation_amount_rub` (денежное выражение отклонения), эта колонка в выводе есть.
5. **Минимум «других» поставщиков для медианы.** Параметр `min_other_suppliers` в Q2 равен 1, то есть дополнительной фильтрации нет — как в постановке. Медиана по одному сопоставителю статистически слаба; в выводе есть `other_suppliers_cnt`, чтобы это было видно. Повышение порога — изменение одного параметра.
6. **Период Q3 не ограничен**, так как в постановке он не задан: расчёт идёт по всему доступному горизонту. Ограничение добавляется фильтром по `dim_date` в CTE `base`.
