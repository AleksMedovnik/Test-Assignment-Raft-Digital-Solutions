# PROC-14 · Витрина сравнения закупочных цен по поставщикам

**Тип:** Task · **Компонент:** DWH / Marts · **Приоритет:** High · **Оценка:** 3 дня
**Эпик:** Аналитика цен (релиз 1, недели 1–4)

---

## Контекст

Ковалёвой нужно видеть, что одна и та же позиция закупается у одного поставщика по 12 рублей, а у другого по 19 — это основной ответ на вопрос Смирнова «где мы переплачиваем» и один из двух измеримых результатов первого релиза. Витрина описана в [02_model.md](02_model.md), каркас есть в [02_ddl.sql](02_ddl.sql). При выполнении Блока 3 в каркасе обнаружен дефект зерна: сравнение идёт внутри базовой единицы, а цена в источнике не масштабируется вместе с упаковкой, из-за чего витрина выдаёт отклонения в тысячи процентов, отражающие тару, а не переплату. Задача — реализовать витрину с исправленным зерном и поставить её на регламентное обновление.

## Что нужно сделать

1. Пересоздать `mart.price_benchmark` с зерном, включающим код единицы измерения.
2. Создать уникальный индекс на зерно (нужен для `REFRESH MATERIALIZED VIEW CONCURRENTLY`).
3. Добавить шаг обновления витрины в ночной пайплайн после загрузки `dds.fact_po_line`.
4. Добавить DQ-проверку сходимости витрины с фактом, блокирующую публикацию при расхождении.

## Границы

**Входит**

- DDL витрины, уникальный индекс, шаг обновления в пайплайне, DQ-проверка.
- Колонка `uom_code` в зерне и признак `has_uom_conflict` из `dds.dim_item` в выводе.

**Не входит**

- Изменения в `dds.fact_po_line`, измерениях и ETL — витрина строится на существующей модели как есть.
- Дашборд и визуализация — отдельная задача.
- Прайсы поставщиков из почты, контрактные цены из SRM, цены маркетплейсов — вне scope релиза ([01_discovery.md](01_discovery.md), «Границы первого релиза»).
- Витрины `spend_monthly` и `price_dynamics_quarter`.

## Входные данные

`dds.fact_po_line`, `dds.dim_supplier`, `dds.dim_supplier_golden`, `dds.dim_item`, `dds.dim_uom`, `dds.dim_date`. Все таблицы уже загружены, изменений в них не требуется.

## Результат

- Материализованное представление **`mart.price_benchmark`**.
- Уникальный индекс `uq_price_benchmark` на зерно витрины.
- Шаг `refresh_price_benchmark` в ночном DAG.
- Метрика `price_benchmark_amount_diff_pct` в `dq.run_metric`.

## Правила реализации

1. **Зерно: `год-месяц × позиция × код единицы измерения × золотой поставщик`.** Код единицы (`uom_code`), а не базовая единица (`base_uom_code`) — это ключевое отличие от каркаса в `02_ddl.sql`. Обоснование и замеры — в шапке [03_sql/q2_price_anomalies.sql](03_sql/q2_price_anomalies.sql); повторять расчёт не нужно, логику сравнения брать оттуда.
2. **Цена = `SUM(amount_rub) / SUM(qty_base)`**, средневзвешенная по количеству. Не `AVG(price)`.
3. **Поставщик — `golden_supplier_id`.** Соединение с `dim_supplier` только по равенству `supplier_key`; соединение по `supplier_id` размножит строки по версиям SCD2.
4. **Фильтры строк:** `NOT is_cancelled AND NOT is_price_scale_suspect`.
5. **Позиции без справочника номенклатуры остаются в витрине** с категорией «Не определена» — оборот не теряется ([02_model.md](02_model.md), «Отсутствующая номенклатура»).
6. Минимальная цена, число поставщиков в группе и переплата считаются оконной функцией внутри зерна, без учёта месяца соседних периодов.

## Критерии приёмки

| # | Given / When / Then |
|---|---|
| 1 | **Given** витрина создана, **when** создаётся `uq_price_benchmark` на `(year_month_key, item_key, uom_code, golden_supplier_id)`, **then** индекс создаётся без ошибки — зерно уникально |
| 2 | **Given** произвольный месяц, **when** сравнить `SUM(amount_rub)` витрины с `SUM(amount_rub)` по `fact_po_line` за тот же месяц с теми же фильтрами, **then** расхождение равно 0 |
| 3 | **Given** позиция, закупленная в одном месяце в `TON` и в `KG`, **then** в витрине это две отдельные строки, и цены между ними не сравниваются |
| 4 | **Given** любая строка витрины, **then** `price_per_base_uom = amount_rub / qty_base` с точностью до 6 знаков |
| 5 | **Given** поставщик с минимальной ценой в своей группе, **then** его `overpay_rub = 0`, а у остальных — строго больше нуля |
| 6 | **Given** заполненная витрина, **when** выполняется `REFRESH MATERIALIZED VIEW CONCURRENTLY mart.price_benchmark`, **then** команда отрабатывает без ошибки и без блокировки читателей |
| 7 | **Given** расхождение витрины с фактом больше 0,01%, **when** отрабатывает ночной DAG, **then** публикация витрин останавливается и пишется запись в `dq.run_metric` с `severity = 'block'` |

## Тест-кейсы

**Позитивные**

1. **Сравнение поставщиков по одной позиции.** Взять позицию с закупками у двух и более золотых поставщиков в одном месяце и одной упаковке (в датасете таких групп 1 036 за квартал). Ожидание: строк столько же, сколько поставщиков; `suppliers_in_group` равен их числу; `min_price_in_group` одинакова во всех строках группы.
2. **Позиция без справочника номенклатуры.** Взять любой из 40 `item_id`, отсутствующих в `items.csv`. Ожидание: строки присутствуют в витрине, категория — «Не определена», оборот учтён.

**Негативные и граничные**

3. **Юаневые закупки исключены.** Ожидание: в витрине нет ни одной строки с `is_price_scale_suspect` (в датасете это 2 533 строки в CNY, отфильтровываются по правилу 4).
4. **Дубли поставщиков схлопнуты.** Взять один из 8 ИНН, за которым закреплены два `supplier_id`. Ожидание: в витрине одна строка на этот ИНН в группе, а не две; оборот суммирован.
5. **Единственный поставщик в группе.** Ожидание: `suppliers_in_group = 1`, `overpay_rub = 0`, деления на ноль и `NULL` в `price_per_base_uom` не возникает.
6. **Отменённые строки заказа.** Ожидание: не попадают в витрину; при их включении оборот вырос бы на 5,88%.
